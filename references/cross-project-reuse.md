# 跨项目检索与复用审查

用于跨任务寻找方法、分析漏召回或处理旧记录的范围冲突。配合 [knowledge-lifecycle.md](knowledge-lifecycle.md) 使用；不要求搭建搜索服务，也不要求普通记录填满本文件所有字段。

## 1. 保留业务问法，解释术语转换

先保存原问题、要支持的方案决策、任务类型和实际约束。检索无命中或大量命中却没有可用证据时，分别检查索引、字段、术语和过滤条件，在既定查询预算内补查。

将业务用语映射为已有库中有依据的表达或流程概念，记录映射来源及其关系：同义表达、上下位概念或仅相关线索。AI 提出的映射先标为建议；读取条目后才能说明它支持哪部分问题。不要把“可用量”与“覆盖率”、“待审量”与“错误量”直接当成同义指标；分子、分母、阶段及完成状态仍按当前任务定义。

补查可以保留业务分支并增加方法分支，例如原词加“分母、待复核”等流程线索。不要只留下抽象词而丢失原始任务条件，也不要将“候选、未执行”等高频状态词的命中数量当相关性。各次查询分开保留结果；合并候选时按 ID/修订去重并保留来自哪次查询。

词表只积累实际用过且解释清楚的少量映射，放在查询记录或已有知识索引中。相关词用于发现候选，不改变条目的业务含义和权限。无需为单个案例建设全局本体、堆入通用关键词或改写原文来强行命中。新的别名若写入索引，保留来源、适用范围和索引版本，并使旧召回回执失效。

## 2. 命中、排序和阅读窗口分别报告

记录实际执行查询、语料版本、过滤条件和返回顺序。当结果被截断或只读取一部分时，记录返回上限与实际阅读范围；不知道后端完整候选数就写未知。

| 观察 | 解释 | 有界补查方向 |
|---|---|---|
| 原业务词没有结果，合理改写有结果 | 在此语料和查询下存在术语缺口 | 保留两次结果与映射理由 |
| 返回很多条，但缺少决策所需的直接依据 | 查询过宽或排序不能优先给出所需证据 | 增加具体问题线索；必要时补查经验/问题类型并保留其他证据来源 |
| 相关条目在已返回候选中，但在阅读窗口外 | 候选已命中，窗口内发现失败 | 在预算内扩窗或补充方法检索；不要计作原窗口已通过 |
| 未知候选池中是否存在目标 | 不能定位到排序阶段 | 先记录未知，不猜测漏召回原因 |

根据方案决策的证据缺口判断是否继续，而不是“找到任意一条即停止”。如果相关方法已经有充分证据，不必为了指定 ID 继续搜索。预算耗尽或接口不支持扩展时报告缺口，不无限扩大 k。

查询改写、扩窗、类型补查或重排均记录前后条件。类型只是检索线索，不能强制“经验永远优于实验”，也不能用已知目标 ID 人工置顶后声称排序变好。排序并列规则、搜索范围与排序范围的差异有影响时说明。案例中的词频排序不代表语义相关性。

按需补充到 `retrieval_check`：

```yaml
query_transforms: null       # 原词、改写词、关系、依据、执行轮次
result_window: null          # 返回上限、总候选数(可未知)、实际阅读范围
target_positions: null       # 有已知相关目标时，ID/修订/查询分支/可观察名次
candidate_found: null
visible_in_review_window: null
selected_for_plan: null
selection_ref: null          # 适用性审查和采用到哪个步骤
diagnosis: null              # 已观察 / 基于日志推演 / 未确定
```

目标相关性和窗口若是在看过日志后确定，要标为事后诊断。事后发现某条在第八位，可以证明“前五条看不到此条”，不能证明该需求所有相关知识均漏掉。只看日志计算窗口也不能写成实际用户或中台漏召回。一次补查找回目标不是检索质量提升评测；泛化效果仍需独立问法、相关性依据和不适用候选。

## 3. 以主张为单位判断适用边界

一条记录可能同时包含方法、参数和效果；`reuse_kind=method` 不能让整篇记录全部变成可迁移方法。对方案真正采用或明确排除的内容，分别说明：

| 层次 | 判断内容 | 可形成的结论 |
|---|---|---|
| 方法 method | 解决什么问题、必要前提是否满足、要适配什么 | 可作为设计参考 / 可进入试行 / 不适用 / 条件未知 |
| 实现与配置 implementation | 输入输出契约、规则、模型、参数及资源可用性是否兼容 | 沿用已验证范围 / 需适配重验 / 不适用 / 未确认 |
| 效果 outcome | 新旧数据、评价范围、标准和执行是否可比 | 仅历史证据 / 当前实测支持 / 未测；不能从方法迁移推得效果 |

对具体条件先区分作用：

- 访问权限与数据使用边界：所有检索分支都遵守，不因方法抽象而放宽。
- 方法必要前提：必须针对该方法核对，如有待审分支、分母可定义；不满足时不能直接采用。
- 实现约束：决定某代码、规则或参数能否执行，通常不决定能否参考其流程思路。
- 证据背景：描述原观察发生的样本、版本和数据哈希，保留供追溯，不自动硬过滤方法参考。

某条件可能同时影响方法和实现，依据具体主张说明，不能一概把“业务域不同”降为软约束。

### 旧元数据与正文冲突

旧条目的 `applicability` 若把整个方法绑定到原数据集，先保留冲突与原版本。只能在有访问权限的材料内另做方法参考审查，不静默绕过原条件或把原条目标为跨项目有效。

正文与证据足以支持某个窄方法时，在新项目记录派生的 `reuse_assessment`，明确哪些条件属于原实现、哪些是新方法前提，以及判断依据。原约束的意义仍不清楚时，只保留候选并列出待确认事项，不能默认允许复用。修改源知识需要有实际范围内的维护任务与证据；本次审查不自动批量迁移旧库。

```yaml
reuse_assessment:
  source: null              # 项目/条目 ID、修订、定位；可附哈希
  target: null              # 新需求/方案及修订、采用步骤
  claim: null               # 实际借用的一条方法、配置或效果主张
  reuse_kind: null          # method / implementation / outcome
  condition_checks: null    # 原条件、作用、当前是否满足、证据/未知
  metadata_conflict: null   # 原文与字段冲突及本次处理
  decision: null            # 方法参考、适配试行、不适用、待确认等
  adaptation: null
  revalidation: null        # 重验对象、判定依据、当前执行状态及结果定位
  reviewed_by: null         # AI / 人 / 工具；不得冒充人工审批
  reviewed_at: null
```

不要求拆成三个新文件；用同一表中的不同列/行即可，但方法、配置和效果不能共用一个“适用=true”。映射到新方案步骤及验收项目后，才形成可审查的复用依据。未提供模型、Agent 或评审资源时保存依赖缺口。

## 4. 方法采用不等于效果验证

分别表达“建议借鉴”“已经实现并运行”“已证明改善质量”。离线回放支持记录和分流能够执行，不能证明新生成质量、人工闭环或训练收益。配置重验须写明要验证的对象和缺失条件，不能仅在表尾笼统写“全部待验证”。

派生经验优先关联原条目和新增适配证据，避免把同一方法在多个项目重复记为独立发现。已有原经验缺少新场景证据时，可保存新项目的试行审查；不因此提升原经验的普适性。SOP 的成熟度仍按关键步骤与验收覆盖判断。
