# 试跑与初步方案评价

评价单位是“方案版本 + 输入数据 + 规则版本 + 资源配置 + 评估口径”。模型可能是其中一个资源；提示词、规则、流程或人工复核变化同样可能影响结果。

本 Skill 记录试跑设计、已发生的执行和评价。只有当前任务已授权试跑且资源、工具和必要条件实际可用时，才参与运行；整理资料或编写方案不隐含上线、批量处理或搭建缺失链路。

## 试跑前值得留下的内容

- **验证问题**：本次要验证哪个方案、哪个假设或哪个改动，而非只写“跑一下看看”。
- **条件快照**：需求、方案、规则、资源、提示词和模型版本；取不到版本时记录可用快照或定位，并说明复现限制。
- **样本设计**：批次/样本 ID、数量、采样方式、重要类别与困难案例。调试用例和最终评价样本分开标识；在同一批数据上反复修正后得到的结果应注明调优影响。
- **参照依据**：人工参考结果、规则判定、可接受输出或已有基线，注明来源和争议处理。独立复核、模型辅助评估和模型自评分别标记。
- **评估口径**：指标定义、分母、阈值及来源；缺少既定标准时提出标为建议的口径，不报告“已达标”。
- **试跑边界**：样本范围、预算或调用量、停止条件、已授权的重试范围。缺少关键运行条件时交付可执行部分与缺口，不循环重试直至得到好结果。

缺少验收阈值仍可报告观察结果；缺少参考答案时可评估格式、覆盖或明确可判定的规则，但不得把这些替代为整体业务准确率。规则冲突会阻断受影响的合格结论，应明确指出。

## 单样本与节点级证据

沿用平台轨迹、表格或已有明细文件，不强制复制成新格式。每条可定位到：

- `sample_id` 与数据集/批次版本、用途（调试/回归/留出评价）；输入定位或脱敏摘要。
- `run_id / attempt_id`、方案与配置版本、实际输出定位；同样本多次运行分别保留。
- `execution_status`（completed / failed / not_run）、`result_origin`（fresh / cache / replay / unknown）。缓存结果需引用原运行和配置；独立重复试跑的稳定性不能靠重复缓存命中证明。
- 参考答案/规则来源及争议情况；检查或评分器 ID/版本、结果、理由与证据。
- 节点级 `trace_id / node_id / parent_node_id`、输入输出定位与状态，按实际可见粒度记录；仅知道整条链路失败时不要编造失败节点。
- 有实际测量时附耗时、费用、人工复核和问题卡引用；同一次运行的重复上报按稳定标识去重。

明细分为完整、部分或仅汇总。报告总量、已取得明细量与未覆盖量；按唯一样本和运行分别计数，不把重试混成更多独立样本。全量指标只能来自对应全量数据或可核验汇总，不能从挑选的失败样本推算总体错误率。

## 将验收标准变成可执行检查

对每条实际采用的标准记录：检查 ID/版本、规则来源、适用样本、输入路径、判断方法、通过条件、检查器/评分器版本，以及执行状态和结果定位。判断方法可为确定性规则、人工或模型；自动化能力缺失时保留待执行的操作说明，不假装实现。

- 确定性检查适合字段存在、标签集合、互斥关系、格式等明确条件；可引用已有脚本、平台规则或本技能的有限检查器。
- 模型评分需要记录模型/提示词/评分尺度版本和人工校准依据；缺少校准则标明局限。人工验收保留判定者或角色、依据和分歧处理。
- 每项结果为 pass / fail / not_run / error，必要时另记有依据的 not_applicable。执行异常、缺少输入或空评测集不能算通过。
- 汇总需要报告已执行覆盖率与未执行项；关键检查未完成时保留结论缺口。组合方案各检查通过只证明所列标准，不自动证明所有业务质量达标。

### 多份结果的验收汇总

先声明验收对象：确切方案／版本、运行与数据范围，以及本次仅评价自动子集还是整个含人工流程。列出该范围的必需检查和范围外事项；标准来源记录为 agreed（已有用户／团队依据）、proposed（演练或待确认建议）或 unknown。沿用已有约定，不为每次记录新增审批。

简单记录用简短文字表达这些区别即可，不要求每次创建验收计划或运行汇总脚本。

保留三种不同结论：运行完成情况、配置检查结果、声明范围的验收结果。例如自动质量报告 pass 而人工复核 not_run，可以支持自动子集的观察，不能作为含人工流程的验收通过。结构 pass 与质量 fail 同时保留；不让“未完成”掩盖已经发现的不合格。

需要汇总本地报告时使用 [summarize_acceptance.py](../scripts/summarize_acceptance.py) 和 [空白演练计划](../assets/acceptance-plan-example.json)。计划引用真实报告的路径、SHA-256 和状态字段 JSON Pointer；脚本按引用读取，不猜测其他工具的 overall 是什么范围。尚未执行的检查明确记 not_run，不创建虚假成功报告。人为选择的报告必须与声明的对象、数据和版本相符；脚本校验文件与状态，不能自动推断跨工具的业务含义。

```text
python <skill-dir>/scripts/summarize_acceptance.py --plan <acceptance-plan.json> --output <new-summary.json>
```

计划字段以示例为准；`coverage` 为 complete_for_declared_scope / partial / unknown，只是对声明范围的检查覆盖说明，不是模型的样本覆盖率。每项检查有 ID、用途与 required；pass/fail 必须来自报告，直接填写状态只允许 not_run / unknown / error 并说明原因。报告引用缺失、哈希变化或状态字段不存在会使该项为 error。

汇总同时输出 `checks_status`、`required_pending`、`required_failures`、`acceptance_status`：

`checks_status` 聚合必需检查；可选检查的失败或待办仍保留在逐项结果中，不隐去。

| 条件 | acceptance_status |
|---|---|
| 任一必需检查 fail | fail，未完成项仍列出 |
| 没有 fail，但必需检查未执行／出错，或检查覆盖不完整 | incomplete |
| 检查均通过但范围覆盖或标准来源未知 | unknown |
| 声明范围的必需检查均通过，标准仅为建议 | provisional_pass |
| 声明范围的检查覆盖完整、均通过，且标准已有约定依据 | pass |

退出码0仅用于最后一种范围内通过，1表示 fail，2表示其余状态或输入／写入错误。所有状态均不能自动授权发布。报告写入新文件并回读；不会修改原报告，也不执行缺失的人工或模型评估。

### 内置离线检查器

[evaluate_checks.py](../scripts/evaluate_checks.py) 使用 Python 3.9+ 标准库读取检查 JSON 和样本 JSONL，输出单样本/单次尝试的结果及检查计数，不调用模型、不访问网络、不运行任意代码。支持 `required_keys`、`nonempty`、`equals`、`one_of`、`subset_of`；`human` 和 `model` 仅报告 not_run。所有配置的检查都视为必检。`subset_of` 允许空数组，要求至少一个标签时同时配置 `nonempty`。

检查配置格式见 [acceptance-example.json](../assets/acceptance-example.json)。这是虚构机标格式示例，规则来源明确标为示例；实际使用时按项目规则调整、设定版本，不能直接当成业务验收标准。`path` 使用相对于 `output` 的 JSON Pointer：空字符串表示整个输出，`/labels` 表示标签字段，`~0`/`~1` 转义波浪号/斜杠；不支持通配符。`equals` 区分布尔与数字，数组顺序有意义。

输入每行是一个样本尝试，至少含非空 `sample_id / run_id / attempt_id`、上述执行状态和结果来源；completed 但缺少 `output` 会产生 error。可带其他证据字段，但脚本不核验远端产物或业务来源的真实性。

```json
{"sample_id":"demo-001","run_id":"demo-run","attempt_id":"1","execution_status":"completed","result_origin":"fresh","output":{"labels":["合格"]}}
```

以上仅为格式演示。运行方式中的占位路径替换为本次实际文件：

```text
python <skill-dir>/scripts/evaluate_checks.py --checks <checks.json> --samples <samples.jsonl> --output <new-report.json>
```

报告含检查/样本文件 SHA-256、验收配置版本、规则引用、脚本版本、执行时间，以及逐项结果。不会把完整输入输出复制到报告。`--output` 必须是新文件，避免覆盖证据。

v0.4 保留原 `overall` 字段以兼容既有调用，并增加 `result_scope=configured_output_checks_only`、`business_acceptance=not_assessed`。不要把该 helper 的退出码0解释成整个项目验收通过。

退出码：0 表示所有配置检查通过；1 表示全部执行但存在不通过；2 表示输入/配置错误、执行异常或有未执行检查。出现后两类结果时汇总为 incomplete，即使其他检查通过也不能报告完整验收通过。输入错误不生成报告；写出异常可能留下不完整文件，脚本不会报告成功，需核验后处理。

此脚本产生的是离线验收报告；是否已入项目库、更新索引或通过召回，仍按 [knowledge-lifecycle.md](knowledge-lifecycle.md) 单独记录。

## 指标按任务选择

以下是候选观察维度，不是统一必填清单或默认达标阈值。采用团队已有定义；否则在方案中解释本次定义。

| 任务 | 可选择的质量维度 | 需要避免的误读 |
|---|---|---|
| 标注 / 机标 | 一致率、各标签错误情况、漏标、冲突和需人工处理比例 | 总体平均值遮住少数重要标签；把有争议参考答案当绝对真值 |
| 内容审核 / 质检 | 漏判、误判、关键规则覆盖、分层结果、人工复核率 | 用所有样本作漏判率分母而未声明；混淆业务失败与运行失败 |
| 合成 | 规则满足、可用样本产出、重复情况、场景覆盖、事实或标签一致性 | 用生成成功或生成数量替代可用性；以生成模型自评替代独立验证 |
| 跨任务 | 耗时、费用、运行失败、重试、人工投入 | 混合不同批量、并发或计费口径；把未知成本记为零 |

每项结果带数据范围、分子/分母或测量方法、证据来源。需要成本比较时区分生成、审核、重试与人工部分，说明哪些未计入；总耗时与单条耗时、平均与尾部延迟不要混写。

## 比较和问题修复

比较对象是 SOP 的交接效果时，使用 [sop-validation.md](sop-validation.md) 分开检查提炼忠实性、实际执行和相对基线的帮助程度，不把业务方案评价或格式校验当成 SOP 效果证明。

1. 对候选方案使用尽可能一致的样本、规则与口径。若不一致，标为不可直接比较或解释限制，不仅排列总分。
2. 保留初始方案和运行结果。修复或优化创建新方案/配置版本和关联试跑，不覆盖原失败结果。
3. 为可复现或重要问题建立 [问题卡](platform-handoff.md)，检索参考项目中的解法，注明适配差异；没有匹配时如实记录检索范围。
4. 修复后区分“原失败样本通过”与“新样本/其他类别上也通过”，检查有无回归。尚未检查的范围保留未知。
5. 多处同时改变时避免单一原因归因；没有基线时给绝对观察结果，不能声称提升。

只有用户或既定评估方案提供了权重及量纲处理方法时才计算综合分；否则按维度比较并解释取舍。推荐某方案可以是基于约束的判断，但需区分实测依据、预期收益和未验证部分。

## 初步方案与评价记录

```markdown
### EV · 需求的初步方案评价

- 对应需求及版本：
- 当前结论：建议进入下一轮验证 / 建议调整 / 暂不适用 / 证据不足等
- 推荐方案 ID/版本及流程：关键步骤、资源引用、人工介入点
- 方案来源：复用 / 组合 / 全新，具体采用的项目经验与调整
- 候选比较：各候选的约束满足情况、试跑证据、优缺点和未选原因
- 试跑概况：数据范围、配置、规则和评估方法；链接实际实验
- 评价结果：质量、成本、时效及稳定性等相关维度；标明实测/估计/未知
- 主要问题及处理：问题卡、已验证修复和仍未解决事项
- 可复用范围：本次证据覆盖哪些场景，不覆盖哪些场景
- 依赖缺口：缺少的链路、配置、数据、权限或规则说明
- 下一轮验证：最关键的不确定性、补充样本和验证动作
- 回写关联：更新了哪些经验、资源适用范围或 SOP；未回写时注明
```

未执行方案可以有设计层面的初步评价，但不能填写虚构运行结果；将预期效果明确标为预测。只有部分候选试跑时，比较表明确各自证据状态。输出是初步方案与评价，不自动代表正式上线结论。

评价发布后若规则、资源或结果被修正，链接新的修订和证据，标明旧评价适用的历史版本；不要把历史达标直接套用到当前版本。

## 给中台自身评测留下案例

在一次项目中已观察到时，可保留“需求—人工认定的相关参考—实际召回—采用方案—试跑结果—人工反馈”的链路，供将来评估召回和方案生成；缺少人工判断不自动制造标准答案。

区分未来可评估的环节：是否找到相关且有权使用的资源、是否正确使用规则、组合能否执行、解法能否解决问题、评价是否受证据支持。沉淀业务案例不等于已建立评测集；形成评测集前应另行核对案例权限、标注依据，以及它与检索/调优材料的隔离情况。
