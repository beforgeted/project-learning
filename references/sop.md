# SOP 的形成、执行与维护

SOP 应让另一位员工在明确条件下复现做法，并判断产出是否合格。步骤可以包含人工判断、提示词、模型调用、平台配置、Agent 链路、工作流或代码。

## 提炼粒度与执行入口

先明确这条知识会改变下一次的哪个决定。能用检查规则或决策表承载的内容，可以关联到已有步骤；一段可重复操作可以形成子流程；完整 SOP 再组织子流程与交接。原始失败和未决尝试继续留档。

将来源中的做法写成“触发条件 → 可观察依据 → 动作/分支 → 原因与例外 → 验证办法”，并链接依据。没有证据的原因保留为假设。抽出子流程时，保留影响执行的前提、异常处理和未覆盖阶段；新增条件要说明来源，不能将提炼时补写的规则冒充原来已经验证。

执行者可先看到准备、操作、检查与异常入口，再按链接查实验和版本证据。沿用现有记录结构，不强制拆文件或复制元数据。清晰程度和篇幅只是设计判断；是否更好用按 [SOP 交接与对照验证](sop-validation.md) 检查。

## 判断成熟度

| 状态 | 使用条件 | 必须说清的内容 |
|---|---|---|
| 草稿 | 主要来自讨论，或关键执行步骤、结果还缺失 | 假设、缺口及验证办法 |
| 试行 | 有执行记录，关键步骤可复现，效果或覆盖范围仍有限 | 已覆盖样本、运行条件、试行验收与停止条件 |
| 已验证（限定范围） | 在声明范围内，有代表性证据、明确验收口径和达标结果，异常处理可执行 | 验证证据、适用边界、验收依据 |
| 待复核 | 新反例、规则或环境变化影响原有依据 | 受影响部分、暂时可用范围和复核办法 |
| 已替代 / 停用 | 有明确替代流程或停用原因 | 替代链接或停止原因、历史适用范围 |

成熟度随证据变化，不要求机械地逐级升级。代表性由任务范围、错误代价和已有验收标准判断；样本数量大不必然代表覆盖充分。单次尝试可成为候选做法，是否足以验证必须说明依据。

“团队已采纳”“用户希望作为标准”是采纳状态，不能代替效果验证。已有业务标准照实使用；缺少标准时，可以提出明确标为建议的试行门槛，不能捏造已批准的阈值。

## SOP 模板

按实际需要缩减字段；不适用的内容可省略。

```markdown
# SOP-001 · 流程名称

- 版本与更新日期：
- 成熟度：
- 团队采纳状态：已知时填写，否则注明未说明
- 目标与交付物：
- 适用范围与不适用情形：
- 依据：方案、实验和经验链接
- 复用条件：需求特征、规则版本、所需资源能力及版本
- 知识有效性：业务有效时间、最近验证、触发复核的变化

## 执行前准备
所需输入、样本或规则版本、平台与模型条件、角色职责、必要权限。
引用可访问的提示词、配置和模板；标明影响结果的可调参数。
资源以已提供的目录 ID/版本引用。允许替换的节点说明替换条件和重验要求；缺少资源时标明依赖缺口，不臆造已上线链路。

区分执行方法、具体配置和效果保证；可以复用评价步骤而重新验证分类规则。案例脚本的固定输入、解析格式和外部命令依赖要列明；在新目录重跑不等于已经验证跨项目使用。

## 操作步骤
1. 动作、使用的输入或配置、预期输出。
2. 下一动作、分支条件，以及什么时候需要人工判断。
按流程复杂度设置检查点，不规定固定步骤数。

## 验收与留档
- 验收对象、方法、范围或抽样方式。
- 指标定义、阈值及其依据；尚无标准时明确标为试行建议。
- 检查 ID/版本、确定性或人工/模型评估方法、输入输出、通过条件及执行结果引用。
- 结果、配置版本、运行标识及异常记录的保存位置。
- 验收对象及必需阶段：仅自动子集 / 含人工闭环 / 其他明确范围；标准已约定还是仅为演练建议。

## 异常与返工
已知异常的识别方式、处置办法、重试或停止条件、人工复核入口。
流程改变线上状态时补充适用的恢复或回退方式。

## 验证范围与已知限制
使用过的批次、场景和评估方式；未覆盖部分、已知反例。
已做交接或版本比较时，关联实际产物与基线，分别说明执行符合约定、相对帮助程度及未测范围；未做则不补写效果提升。

## 维护记录
版本 / 日期 / 改动及原因 / 新证据 / 对适用范围或成熟度的影响。
```

SOP 中的提示词应可定位到版本或保留可复用正文，不能仅写“用之前那个提示词”。平台界面步骤应引用实际查看的配置；不知道具体菜单时描述需要达成的操作并注明待核实，不虚构按钮路径。

运行入口与验收入口应指向同一批次、运行和输出版本。允许新目录复跑时，一并检查验收工具如何选择新产物；固定读取旧目录的校验器只能证明旧结果。语义质量未检查时，真实合格量仍未知；如报告“已确认通过数为零”，须与已评审数量和未评审数量对应，不能被当作总体质量为零。

当拒收、去重、隔离与分组/聚合相互影响时，分别写明主路由优先级、每项信号的参与集合，以及过滤、去重、聚合的顺序。样本主路由为拒收，不自动意味着它已经从所有分组或统计中移除。例如同组含一个有效答案和一个空白答案时，“全部字符串记录分组”与“仅结构有效记录分组”会给有效答案不同的多答案标记；两者不能仅凭高优先级拒收规则相互推导。沿用已明确的业务政策；本次采用的试行解释注明来源与范围，不自动提升为跨项目默认规则，也不为记录这一选择额外增加审批流程。

分开报告原始行数、进入分组的成员数、不同答案数、组数和互斥主路由数量；只记录本任务实际需要的口径。若比较不同分组解释，说明是参考重算还是完整流程实际执行。执行与声明一致只证明该解释被实现，不证明它是业务上唯一正确或已被团队采纳。

## 更新与复用

1. 定位新证据影响的结论、条件或步骤，检查相关 SOP。
2. 判断是局部补充、缩小范围、需要复核还是替代。保留仍有证据支持的部分，说明本次影响。
3. 更新版本与维护记录，保留旧验证依据及其历史范围。不能只更新措辞而保留已经不成立的“已验证”状态。
4. 链接新的实验和经验，更新项目索引。
5. 跨项目复用前核对输入类型、规则、模型/平台、质量要求和人工复核条件。差异较大时以草稿或试行形式验证，不能直接继承原验证状态。

SOP 作为中台的候选方法被召回时，应附适用条件、资源依赖、证据与未覆盖范围。中台采用 SOP 生成的方案仍需要针对新需求试跑；历史成熟度不能替代本次方案的评估。

有跨项目复用时，将 [cross-project-reuse.md](cross-project-reuse.md) 的审查映射到 SOP 步骤：借用的方法、适配后的配置、待验证效果分别注明。仅新增记账或分流的执行证据，不足以升级生成、人工质检或训练等未执行步骤的成熟度。

已验证 SOP 的关键验收项目需要有实际执行结果；未运行、评分器错误或仅格式检查通过不能替代业务验收。记录首次发布或重要修改后的业务召回检查和独立交付回执，详见 [knowledge-lifecycle.md](knowledge-lifecycle.md)。

业务流程没有达标，不必否定已验证的记录或评价步骤；但这些步骤通过也不能提升整个业务 SOP 的成熟度。必要时只对已覆盖子流程作有边界的结论，完整 SOP 保留试行和未完成项。

只有用户要求执行 SOP 时才按实际授权运行相关操作。请求“整理成 SOP”本身不代表要求启动平台任务或修改生产流程。
