# 面向模型评测中台的知识采集约定

服务于“需求 → 召回知识和资源 → 生成方案 → 试跑 → 检索问题解法 → 初步方案与评价”的流程。本文件规定现在值得积累的字段，不实现中台、资源目录服务或 Agent 链路。

## 知识对象及关系

| 对象 | 建议 ID 前缀 | 保存内容 | 主要关联 |
|---|---|---|---|
| 需求 requirement | RQ | 任务、输入输出、规则、约束和成功条件 | 规则资源、候选方案 |
| 资源 resource | RES，已有目录 ID 优先 | 已提供链路、项目文档、规则文档、数据集、评估器等的能力与定位 | 目录版本、适用需求、使用它的方案 |
| 方案 approach | A | 复用、组合、新建的选择与步骤 | 需求、参考项目、资源、经验 |
| 试跑 experiment | E | 条件、版本、实际结果与限制 | 方案、上游试跑、问题 |
| 问题 issue | I | 现象、条件、失败做法、解法及验证 | 发生试跑、参考项目、修复试跑 |
| 经验 lesson | L | 有条件支持的结论、反例与失效条件 | 支持/反驳的试跑、问题、SOP |
| SOP sop | SOP | 可复用步骤、适用范围、资源依赖与验收 | 原始经验和验证证据 |
| 评价 evaluation | EV | 初步推荐、比较依据、证据与缺口 | 需求、确切方案版本、试跑和问题 |

至少能沿“需求—方案—所用资源与规则版本—试跑—问题/经验—评价”定位依据；有成熟方法时再链接 SOP。没有发生的阶段不造记录。多人或多项目共享时 ID 使用项目命名空间或已有平台 ID，不能只引用一个裸的 `E-001`。

## 公共字段：便于后续解析与召回

沿用现有结构化字段；否则在一个条目下放置一个 YAML 元数据块，再写正文。下面是**空白模板**，`schema_version` 仅为本 Skill 的采集格式版本，未来中台可另做映射。也可用等价的现有数据库字段；不要同时维护两份主数据。

```yaml
schema_version: "project-learning/0.5"
id: null
project_id: null
record_type: null
title: null
revision: "1"
task_types: null
scenario: null
tags: null
evidence_scope: null
reuse_kind: null
reuse_assessments: null
applicability:
  requires: null
  excludes: null
status: null
updated_at: null
access_scope: null
sources:
  - kind: null
    locator: null
    version: null
relations: null
admission: null
validity: null
delivery: null
acceptance_summary: null
```

- `id / project_id / record_type / title`：保存时根据实际项目生成稳定标识与类型。资源 ID 已存在时保留原 ID，必要时加来源系统命名空间。
- `task_types / scenario / tags`：使用团队已有词表；未建立时沿用业务原词，可选标注、审核、合成、质检等多个标签。不要擅自创建大型分类体系。
- `evidence_scope`：实际验证发生的数据、规则、资源、范围和引用。原数据集哈希通常属于此处或 sources，而非所有新项目都必须使用的输入。
- `reuse_kind`：有助于复用判断时注明 method（方法原则）/ implementation（具体实现）/ outcome（效果结论）。一条记录混有不同范围的结论时分别说明，不靠同一标签整体提升。
- `reuse_assessments`：跨项目采用或排除的重要主张及其审查定位；可以链接已有表格，不必重复存储。按 [cross-project-reuse.md](cross-project-reuse.md) 记录来源修订、目标步骤、条件作用、冲突、适配和重验。主张不同可有不同判断，缺少审查不能默认为全部适用。
- `applicability`：下一次复用必须满足的条件及不适用条件，如模态、语言、标签体系或规则版本；仅填写有依据的限制。应与正文一致，不从 evidence_scope 自动复制。
- `revision / status / updated_at`：版本与状态按对象类型记录；这里的记录修订号不代替模型、数据或规则的实际版本。修订时保留变化依据。
- `access_scope`：已有可见范围或使用限制，未知时明确未知。记录标签本身不构成权限控制，也不授权跨项目读取或传播原始数据。
- `sources`：每项带来源类别、能定位的文件/页面/运行或讨论位置，以及已知版本。关键结论在正文中指向具体来源；不把一个文档链接作为所有结论的统一证据。
- `relations`：有关系时使用 `relation / target_id / target_revision / locator`，如 `addresses`、`uses`、`derived_from`、`tested_by`、`supports`、`contradicts`、`supersedes`。新版本不抹去历史关系。
- `admission / validity / delivery`：分别记录经验入库判定、业务有效性和保存/索引/召回回执；按 [knowledge-lifecycle.md](knowledge-lifecycle.md) 填写，缺少信息保持未知，避免一个 status 混合所有含义。
- `acceptance_summary`：需要时引用声明了验收对象、标准来源、未完成项的汇总；不能仅引用一个无范围的 overall=pass。
- `null` 表示未知或未采集；`[]` 仅表示已确认没有条目。日期使用实际已知的日期或含时区时间；不补造实验发生时间。

保存后复核 ID、类型、来源定位和关键关联。正文承担细节，元数据承担检索线索，不把长篇日志或未经验证的推断塞入标签。

旧 0.2 / 0.3 / 0.4 记录可继续读取；只在实际修改时补充适用的新字段并标记 0.5，不补造过去的验证或回执。缺少新字段时按正文与已有证据判断，不能默认其已经核验。无适用字段保持 null；不强制批量迁移。本次仅扩充采集字段，三个离线检查器原有输入输出 schema 不变。

## 需求卡

```markdown
### RQ · 需求名称

- 任务与业务场景：标注 / 审核 / 合成 / 质检及实际目标
- 输入：模态、语言、格式、规模、关键分层及样例引用
- 输出：字段、标签体系、审核动作或合成内容要求
- 规则：权威文档 ID/版本、生效范围、冲突与待澄清项
- 硬约束：质量底线、时间/成本上限、数据处理或平台约束（有依据时）
- 优化偏好：质量、成本、速度等的优先级；未知不自定权重
- 验收：指标定义、阈值、参考答案或判定方式及来源
- 已有资源：用户提供的目录或资源卡引用
- 关键未知：影响召回、组合、试跑或结论的缺口
```

初次记录仅需提取已知信息；未知项不是停止所有记录的理由。涉及试跑或验收的关键缺口按 [evaluation.md](evaluation.md) 处理。

## 资源卡：已有资源的引用与能力说明

```markdown
### RES · 资源名称

- 类型与目录定位：Agent 链路 / 项目文档 / 规则 / 数据 / 评估器等
- 资源 ID、版本或快照、维护方（已知时）：
- 能力及依据：提供方说明 / 已查看配置 / 已验证试跑，分别注明
- 输入约定：必需字段、格式、模态及限制
- 输出约定：字段、结构、错误或不确定状态的表示
- 可配置项与依赖：规则、提示词、模型、其他资源
- 执行入口与运行依赖：实际命令／平台入口、运行时、外部工具及输出含义；仅对可执行资源填写
- 可迁移性：案例专用适配 / 已验证组件 / 已提供平台能力等；已验证的输入变化与仍写死的条件
- 适用范围、限制及不适用条件：
- 生命周期：提供方标示的上线 / 试验 / 停用等状态
- 可用性：本次是否能访问或调用、检查时间、缺失权限或配置
- 已知效果：仅引用具体场景和版本下的试跑评价
```

文档资源只需相关的定位、版本、覆盖范围和来源等字段，不要求填写调用接口。资源未提供时写“待提供”，不生成虚构链路 ID、API、配置或性能指标。只知名称时可以登记资源卡，但标明不足以判断可调用性或组合兼容性。

在新目录重跑相同材料只证明复现，不证明支持新项目。项目专用脚本即使可重跑，也须暴露固定的业务域、记录数量、解析格式或外部工具依赖；未做可迁移性验证时不登记为通用组件。沿用实际 YAML、JSON 或平台字段，并确认读写方支持同一格式，不要求每个项目编写新解析器。

## 方案与召回依据

方案正文沿用 [records.md](records.md) 的模板，补充以下判定：

1. 记录查过的资源范围、查询条件，以及真正采用或排除的重要参考。不保存无价值的检索流水。
2. 分别说明业务相似、输入输出相容、规则适配、证据强度和当前可用性。访问权限或硬约束不满足的候选不能仅凭相似而采用。
3. 明确复用了什么、改了什么、新增什么。每个步骤引用资源/规则/经验的 ID 和版本；新组件标为设计或待实现。
   对混有方法、配置、效果的来源分别审查，按 [cross-project-reuse.md](cross-project-reuse.md) 把适配和重验映射到具体步骤；不能以原记录一个状态替代三类结论。
4. 组合资源时检查字段映射、标签/规则含义、错误状态、重复处理、人工复核入口及已知容量限制。缺少契约时记录未确认，不宣称组合可运行。
5. 当前需求的有效规则优先用于验收；历史项目中的规则是参考证据。规则冲突未澄清时说明影响，不靠“文件更新更晚”或多数项目的做法自行判定正确标准。

可以只提出一个有依据的候选，也可以保留多个实际有差异的候选；不为满足数量编造方案。

## 问题—解法卡

```markdown
### I · 便于检索的问题名称

- 发生位置：项目、方案/资源版本、试跑及节点
- 现象与影响：可观察输出、错误类别、影响范围或样本
- 触发条件：任务、数据分层、规则、输入形态及运行条件
- 检索线索：业务现象、同义表达、错误码或标签等已知项
- 定位证据：产物/日志/样例；根因已确认还是推测
- 参考案例：来自哪个项目、为何相似、关键差异
- 尝试过的办法：改动、结果；保留无效或有副作用的做法
- 当前解法及前置条件：适用步骤、资源或参数变化
- 验证：待验证 / 仅原失败样本有效 / 新样本复验有效 / 无效等真实范围
- 回归影响：是否损害原先正常样本或其他指标；未检查则明确未知
- 关联：原试跑、修复试跑、经验和受影响 SOP
```

现象相似不代表根因相同。先核对条件再借用解法；只有建议没有复验时保持待验证。问题修好也保留失败证据，供中台识别不适用方案和重试边界。

## 中台接入前的最小交接

交接可访问的项目索引、上述对象及关系、实际来源定位、资源目录映射和已知缺口。标明资料仅本地保存、已入共享库还是已完成平台导入；只在看到对应操作结果后声明后两者。

交接包括最近的经验入库依据、有效范围、单样本证据定位、验收配置与执行结果，以及分阶段回执。无外部索引时如实交付本地记录；后续导入使用真实目标的回执继续更新状态。

中台接口确定后再做字段映射、索引与检索接入、权限过滤、运行结果回写和版本失效处理。现在不预设向量库、数据库、工作流产品或最终 API。
